# 搜索空间扩展与阶段决策

研究记录，2026-10-30。本文只分析现有记录与源码，不包含新的 GPU 测量。当前证据范围为 RTX 4090 上 1D FP32 C2C forward、out-of-place、单 upload、热缓存条件。建议的扩展和阈值均为待实验检验的研究方案，不是对 VkFFT 全部合法计划的结论。扩展实验现以单独的[预注册协议](../expanded_search/study_protocol.json)为准。

## 已知结果与未解问题

| 证据 | 支持的结论 | 不能推出 |
|---|---|---|
| N=256、batch=4096，候选相对原始头文件默认时间比 0.891159 | 同 radix 下调整分组及随之变化的实际布局有一个经独立配对验证的收益，时间下降约 10.88% | 收益由单一变量造成，或冷数据、应用端到端也有同等收益；这一案例没有比较其他 radix 分解 |
| N=1024、batch=16，两组 radix 在两个 group 水平下排序反转，经独立随机区组复测 | 所测局部存在 radix × group 的排序交互 | 四点均比默认慢，不能证明 radix 调优能战胜默认 |
| 三个小 batch 的受限空间，最佳非默认独立复测均慢于默认 | 已测范围内应保留默认回退 | 全空间默认最优，或 radix 不值得扩展 |
| 公开 knob 请求出现源码折叠 | 请求值不等于不同执行结构；应检查实际结构和源码 | 源码相同就足以证明所有运行计划状态相同 |

## 现有枚举排除了什么

| 维度 | 当前实现 | 后果与优先级 |
|---|---|---|
| radix 首尾 | [decompositions](enumerate_joint.py#L14) 固定两端，仅重分解中间；默认至多两级则原样返回 | 优先扩展。N=256、batch=4096 的 `[16,16]` 根本没有其他 radix 请求，因而无法判断是否错过主要收益 |
| 因子与寄存器 | 只用 2、4、8、16、32；检查现有表中可整除的逻辑寄存器数、并要求所用阶段 min/max 等于默认包络；boost>1 的末级例外。见[枚举预筛](enumerate_joint.py#L60)与[注入校验](direct_candidate.hpp#L24) | 排除包络变化的候选；这是一种保守实验条件，不是该方案非法的证明。改变分解要重新规划相关寄存器状态 |
| FFT 线程维 | 沿用默认计划中代表 FFT 的线程维；group 来自 batch 的二次幂因子 | 只覆盖这一线程维附近的 group/布局。更改线程维需要与寄存器、共享内存及访存逻辑联合规划 |
| block 和 group | [枚举器](enumerate_joint.py#L38)按观察到的规则预测 block；hook 写入 group，[block 请求只做匹配检查](prepare_direct_headers.py#L67) | 不能把它描述为任意、独立的 `blockDim` 搜索。group 改变还可触发轴交换、读写策略与资源变化 |
| 问题范围 | 单 upload、1D、FP32、二次幂、长度不大于 8192；排除 Rader/Bluestein、R2C 等，batch 分组仅取整除的二次幂 | 不覆盖一般 FFT 或不同架构。先完成当前范围的可行性与收益评估，再分支扩展 |

### N=256 数学覆盖计数

在独立的纯数学空间里，允许的 radix 集合为 `{2,4,8,16,32}`，顺序视为不同，乘积为 256 的有序分解共 **120** 个，首尾均为 16 的只有 `[16,16]`。这不是 VkFFT 合法率或性能估计；实际有寄存器表、资源、代码生成和数值限制。以下 Python 3 代码可直接复现，无需 GPU：

```python
from collections import Counter

radices = (2, 4, 8, 16, 32)

def decompositions(remaining):
    if remaining == 1:
        yield ()
    for radix in radices:
        if remaining > 1 and remaining % radix == 0:
            for tail in decompositions(remaining // radix):
                yield (radix,) + tail

sequences = list(decompositions(256))
fixed_ends = [s for s in sequences if s[0] == s[-1] == 16]
counts = dict(sorted(Counter(map(len, sequences)).items()))
assert len(sequences) == 120
assert fixed_ends == [(16, 16)]
assert counts == {2: 3, 3: 18, 4: 35, 5: 35, 6: 21, 7: 7, 8: 1}
print(len(sequences), fixed_ends, counts)
```

实测输出：`120 [(16, 16)] {2: 3, 3: 18, 4: 35, 5: 35, 6: 21, 7: 7, 8: 1}`。数学空间中数量巨大不意味着这些候选中一定有收益。

## 扩展路径及依赖

1. **先做默认多重集排列的受限探针。** 仅支持单 upload、无 Rader/Bluestein、二次幂、`registerBoost=1`，候选与默认拥有相同 radix 多重集，允许两端变化。一个可审查的实现位置是调度器[默认 stage 构造后](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3230)、[最终 min/max 检查前](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3256)，并避免[自动交换首级](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3279)覆盖用户请求。候选必须随后经过 min/max 重算及写回，不能复用旧计划的衍生数据。此办法只检验排列，`[16,16]` 的多重集只有一个排列，解决不了该例的分解覆盖。
2. **再支持因子多重集变化。** 将完整候选纳入调度阶段，重建与候选相容的 `loc_multipliers`，复核[寄存器表生成](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3015)、[radix 内核优化](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3197)、stage、min/max 与 `usedLocRegs` 等依赖；优化器可能改变分解，应记录实际结果并验证是否满足请求。这里需要实现和验证，不能仅放宽后置的 `stageRadix` 覆盖检查。扩大 `registerBoost` 还要处理[专用末级的选择与追加](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L3209)，暂列后续工作。
3. **重新运行完整计划与验证。** 改变首末级影响[读取路径](../../../VkFFT/vkFFT/vkFFT/vkFFT_CodeGen/vkFFT_KernelsLevel1/vkFFT_ReadWrite.h#L38)和[写入路径](../../../VkFFT/vkFFT/vkFFT/vkFFT_CodeGen/vkFFT_KernelsLevel1/vkFFT_ReadWrite.h#L116)；须以新序列重建 [LUT](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_Plans/vkFFT_Plan_FFT.h#L236)、经 [splitter](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_Plans/vkFFT_Plan_FFT.h#L452)重算布局，再生成、编译，检查实际请求匹配、编译后资源和多模式全输出正确性。默认计划、identity hook、原始头文件对照均要保留。通过这些检查是该实验中的准入条件，仍不是任意设备上的合法性证明。
4. **线程维与寄存器包络是更高风险的下一层。** [splitter](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_AxisBlockSplitter.h#L262)从 `fftDim`、`min_registers_per_thread` 和 `registerBoost` 推导 FFT 线程维并受资源限制。若改变其中一个，应重新运行关联资源与索引推导，不能通过单独覆写 local size 声称覆盖了合法 block 空间。

## 评估设计和决策

这里的候选耗时比定义为同一轮 `candidate/default`，小于 1 才表示时间下降；速度比是该值倒数。一个经确认的“radix 收益”应保持问题与 group 等受控条件一致，并在实际结构记录中确认 radix 不同；如果改变 radix 同时触发 block、寄存器或读写变化，应称为**radix 请求诱发的计划变化收益**，不能把全部收益归因于某一级蝶形。比较旧与扩展搜索时同时报告不限制 group 的联合最佳，以评估实际计划收益。

预先指定至少五个新增 `(N, batch)` 工作负载，覆盖多个二次幂长度、大小 batch、不同默认 stage 数；避免把先前四组已用于选择结论的工作负载当作新增验证集。对每组保留原始默认、旧空间与扩展空间候选，先多输入正确性筛查，再随机区组比较。选择出的候选在新进程及新会话中进行与默认、旧空间最佳的配对复测；记录扩展空间的每种拒绝原因与生成、编译、验证耗时。固定候选数和固定总墙钟预算分别比较；对随机搜索重复多个种子。赢家选择后不复用筛选数据当确认数据。

当前实际实验使用[固定协议](../expanded_search/search_protocol_v2.json)：每工作负载至多 64 个非默认请求，依据 stage 数、多重集、静态预测线程维和 group 分层。按 stage 轮转并非对全部结构均匀采样，可能使极端 stage 数或寄存器取值相对于其在空间中的占比权重过高；模型外推与命中率不能据此推断。不得根据中途性能改变本轮选点。后续可在新的、独立注册协议下对比结构均匀分层、默认附近启发式和随机搜索，并按共同候选数与墙钟预算报告。默认是强基线，若扩大空间仍未发现收益，仍可报告这次有边界的覆盖；它不证明 VkFFT 或本原型在完整空间全局最优。

| 观察结果 | 决策 |
|---|---|
| 数值错误、请求和实际结构不一致、超资源或 identity 对照异常 | 停止对该候选做性能解释，修复并重新验证；报告拒绝和失败率 |
| 新增五个工作负载均没有稳定 radix 收益 | 暂不训练模型；检查覆盖、允许的分解和候选生成，再决定是否调整研究范围。无显著收益不等于证明不存在收益 |
| 至少一个预注册工作负载有实际可用候选，两次独立确认会话中配对时间的点估计均下降至少 2%，且各会话 95% 区间上界均低于 1.0 | 继续在更多长度上复核；2% 是预先指定的实用门槛，不是硬件定律。须保留各工作负载结果及选择过程，避免把多重探索结果描述为总体概率 |
| 扩展空间候选较多但相同预算下不优于旧空间/简单随机搜索 | 收缩生成范围或改进候选优先级；不要用无预算穷举赢家证明在线方案有效 |
| 只有热缓存收益或规划成本超过节省 | 分开报告热缓存、冷流式和不同复用次数下的收益；未测场景保持未知 |

区间只表征相应会话及所用区组的统计假设；需跨会话复测，不将同一会话重复样本当成跨设备独立样本。对于极短 kernel 的计时、赢家偏差和多重比较，应报告完整候选清单和区间，不只展示赢家。

## 何时、怎样测试模型

只有上述扩展和对照证明存在可重复、可获取的收益后，才开展小预算模型探索。比较默认、简单规则、受约束均匀随机、基于请求参数的模型和基于**编译前实际计划描述**的模型；候选预算可预注册为 1、4、8，默认的生成与验证、失败候选、推理以及全部搜索成本按统一口径计入，报告各预算下的对默认胜率、最坏回退、top-k regret、编译次数及墙钟。分析不同计划复用次数的总成本，必要时明确不调优。

以完整工作负载分组划分训练、调参、测试；同一 `(N, batch, device, transform, placement)` 的候选、随机种子、重复及其等价源码不得跨折。按长度族留出做主要泛化测试，超参数只在训练/验证折中选择；另以整种 GPU 架构留出评估跨架构，两个 RTX 4090 实例不能替代。编译前模型不可使用真实编译寄存器、运行时间、测试集统计、赢家标签或仅靠编译后才能知道的哈希作为输入；编译后哈希只能用于审计、去重或标注，不得通过测试信息反向影响训练。现有几个工作负载不足以支撑泛化评价。

## 已有研究与创新边界

- [Dotsenko 等，Auto-tuning of Fast Fourier Transform on Graphics Processors，PPoPP 2011 原文](https://www.microsoft.com/en-us/research/wp-content/uploads/2011/02/PPOP11.pdf)：讨论 radix 排列、单 FFT 线程数、block 内 FFT 数、寄存器/共享内存启发式，并编译测量 probe 以缩小搜索。不能将 FFT 的这些基本调优维度或 probe 搜索笼统宣称为首创。
- [Fraguela、Voronenko、Püschel，Automatic Tuning of Discrete Fourier Transforms Driven by Analytical Modeling 原文](https://spiral.ece.cmu.edu/pub-spiral/pubfile/pmespiral_136.pdf)：用包含内存系统的模型指导 SPIRAL 的 FFT 搜索；文中还引用了基于 FFT 递归特征的机器学习工作。它是 CPU 模型，不是本 GPU 场景的性能证据。
- [Ansor，OSDI 2020 原文入口](https://www.usenix.org/conference/osdi20/presentation/zheng)：使用分层程序空间和学习代价模型；一般性的结构表示加学习排序已有先例。
- [Optimal Kernel Tuning Parameter Prediction using Deep Sequence Models，2024 预印本](https://arxiv.org/abs/2404.10162)：结合参数预测与硬件约束 beam search，针对卷积而非 FFT。
- [A Two-Stage GPU Kernel Tuner，2026 预印本](https://arxiv.org/abs/2601.12698)：将参数化模板与约束搜索结合，研究其他 GPU kernels；不可把其收益转移到 VkFFT。
- [Benchmarking optimization algorithms for auto-tuning GPU kernels](https://arxiv.org/abs/2210.01465)：比较不同调优时间预算下的搜索表现，支持在共同预算和多次随机运行下评估。

可检验的具体问题是：在明确 VkFFT 支持范围和正确性前提下，编译前可得的计划信息能否在相同预算中比默认和简单搜索更可靠地找到收益，并且包括规划成本后仍有价值。目前没有模型结果，也不作创新性结论。
