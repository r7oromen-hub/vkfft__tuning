# 混合因子与多上传：当前覆盖和后续路径

## 当前处置

本轮 **未实施、未测量**混合因子长度或多 upload 的候选搜索，不能由 28 个二次幂、单 upload 负载的结果推断这两类覆盖或收益。候选接口在 [candidate.hpp:40](candidate.hpp#L40) 强制长度为二次幂，并在 [candidate.hpp:44](candidate.hpp#L44) 将 radix 限于 2、4、8、16、32；[enumerate_candidates.py:10](enumerate_candidates.py#L10) 也只枚举该域。[prepare_headers.py:75](prepare_headers.py#L75) 和 [prepare_headers.py:165](prepare_headers.py#L165) 要求恰为一个 upload、`registerBoost=1`。这些是研究原型限制，不能据此断言 VkFFT 本身不支持其他情况。已有 `[8,8,2]` 等是由不同的**二次幂 radix**组成的序列，不是本文所说含 3、5 等因子的混合长度。

>L2 rotation 只是对已经通过双会话确认的同一类单 upload 计划改变地址池的条件实验，不增加 radix 类型或 upload 数；它既不覆盖混合因子，也不覆盖多 upload，且不等于实测 cache miss 或冷缓存。若没有通过门票的候选、预算或设备执行不足，该实验本身仍属未覆盖。

## 为什么不能直接放宽白名单

对混合因子，当前 [candidate.hpp:51](candidate.hpp#L51) 重建的是二次幂 radix 的统一寄存器表，未建立含 3、5 的各 radix 表和原调度器可能需要的非均匀寄存器包络。原始 [VkFFTGetRegistersPerThread](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L308)、[VkFFTOptimizeRadixKernels](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L1958) 与 [VkFFTMinMaxRegisterCheck](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L2164) 联合确定乘子、各 radix 的寄存器、阶段和资源约束，后者还处理 Rader 容器。分解含较大素因子时，调度还可能选择 [Rader](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L2288) 或 [Bluestein 及其 padding](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L2405)；并非所有含非 2 因子的长度都会走这些路径，也不能把它们混为一类。

对多 upload，调度器先决定 pass 数和每个 pass 的 [axisSplit](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_HostFunctions/vkFFT_Scheduler.h#L2602)，每个 pass 的局部长度、寄存器表、布局和资源都依赖该切分。[FFT 计划](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_Plans/vkFFT_Plan_FFT.h#L133) 进一步根据 axisSplit 计算首阶段大小，并处理 [reorder、临时缓冲与 stride](../../../VkFFT/vkFFT/vkFFT/vkFFT_PlanManagement/vkFFT_Plans/vkFFT_Plan_FFT.h#L191)；[运行路径](../../../VkFFT/vkFFT/vkFFT/vkFFT_AppManagement/vkFFT_RunApp.h#L114) 按 upload 顺序发射多个 axis。当前请求只描述一个 stage 列表、一个 R 和一个 group，其乘积校验、结构快照及单 kernel 图假设不能代表整个多 pass 计划。只修改 stage 数组或去掉 `numAxisUploads == 1` 检查会绕开这些依赖，并不能证明结果正确。

## 后续可审查的安全路径

1. **单独注册混合因子、单 upload 试验。** 先只读采集原始默认计划，选择可直接使用 2、3、5 的小长度及多个 batch，以实际计划排除 Rader、Bluestein 和多 upload；逐项记录是否满足条件，而不是预先假定所有候选可用。以独立 CPU 或解析参考验证全部输出。先做到原始默认、无请求的实验头默认和可表达的 identity 在源码、完整描述及输出上相等。
2. **在 scheduler 的依赖生成前表达候选。** 设计能够保存每 radix 合法寄存器值、min/max、乘子和阶段顺序的请求与描述；明确沿用哪些原始推导、哪些必须基于候选重新计算，并验证优化后实际结果与请求一致。不可先假设非 2 因子也适用本轮统一 R 表。重新计算实际 FFT 线程维、共享内存和寄存器约束后再生成 LUT/代码，记录编译资源、实际布局及异常拒绝。先用 CPU 单测和身份对照，再进入小规模 GPU 数值准入；准入失败不进入性能搜索。
3. **将 Rader/Bluestein 作为独立后续范围。** 审查 prime 容器、嵌套阶段、padding、卷积与辅助计划和缓冲等完整依赖；先建立默认身份、每 kernel/辅助计划结构和端到端数值证据，再谈候选。此处没有声称已经完成这些实现。
4. **另立多 upload 原型与协议。** 首先只观察原始默认的 upload 数、axisSplit、每 pass 的 stage/寄存器/布局、发射顺序、缓冲、stride、重排及临时存储，记录各 kernel 的源码、编译参数与资源。请求应针对实际 pass 局部长度且表达完整计划；候选变更后由调度器重新推导全部受影响的 pass 和全局索引。须为多 kernel FFT 重新定义图节点期望并计时一次完整变换，完整检查输入保持、输出数值及多 pass 顺序；不要复用本轮单 kernel 节点数量断言。
5. **先验证身份、正确性，再做有预算比较。** 每类分别预注册 workload 与搜索预算，保留原始默认回退、不可表示和未测状态；对满足静态与编译资源约束的候选进行多模式、多 seed 全输出核验。若候选或身份不一致则停止该范围。性能使用原始默认配对、独立会话与完整成本口径，避免将某个 pass 的改善误称为整个 FFT 的改善。每一阶段是否实施以可用时间、覆盖价值及先前有效结果为依据，本文件不是对 GPU 实验已经完成的声明。
