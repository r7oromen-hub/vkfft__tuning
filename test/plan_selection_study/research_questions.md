# VkFFT 计划选择研究：问题、证据与停止标准

本轮重新采集独立数据，研究对象固定为 VkFFT 1.3.4、CUDA、FP32、1D、2/3/5-smooth、C2C forward、独立输入输出、自然输出顺序和单 stream。上游提交为 `066a17c17068c0f11c9298d848c2976c71fad1c1`。准确矩阵、候选字段、统计规则和预算见 [research_design.json](research_design.json)；运行前保存该文件 SHA256，后续协议变更必须留痕。

旧实验只用于发现问题、设定候选和数值门槛，不能混入本轮效果估计。旧数据中的局部约 2 倍差距是探索性线索，不能代替完整独立复测。旧实验的共享 GPU 干扰也说明，数值正确不代表性能测量有效。

## 三个核心问题与一个辅助问题

| 问题 | 所需证据 | 不能由此推出 |
|---|---|---|
| H1：默认启发式何时落后、差距多大？ | 所有预定请求的有效性账本；默认与筛选选中候选的独立复测；改善、无改善和退化一起报告 | 测试集合最优就是全部合法算法的全局最优 |
| H2：哪些实际结构有区别，取舍是否随 workload 改变？ | 参数到解析配置、核心结构、源码/编译输入的折叠；完全相同候选 ID 的跨 batch 排名；独立确认交叉方向 | 名义参数不同就有不同 kernel；只有 upload 数量能解释所有差距 |
| H3：规划与搜索的成本是什么，能否在编译前实际得到结构？ | 分阶段计时；真正零编译/零模块加载/零 kernel launch 的 describe；与 full 构建一致性；同 context 枚举成本 | 初始化时间等于编译时间；编译前日志等于免编译；已知离线 winner 等于部署了学习选择器 |
| H4：结构特征能否帮助跨 N 选择候选？ | 固定模型/特征消融、按 N 分组留出、选择遗憾与默认相对性能 | 模型准确率可以替代 H1–H3；一个设备上的小样本能够证明广泛泛化 |

H1–H3 是主证据。H4 始终是辅助可学习性检查，不能用一张模型图弥补性能空间、工作负载取舍或成本证据的缺失。

## 固定范围与候选覆盖

16 个长度固定为 256、1024、8192、12288、16384、20480、32768、49152、65536、81920、131072、196608、262144、655360、786432、1048576。每个 N 测 B=1 和 B=floor(2^25/N)，大 batch 输入最多 256 MiB。12288、16384、20480、65536 另外测 B=16，共 36 个 workload。

矩阵覆盖短变换、单/多 upload、2 次幂和含 3/5 因子的长度，以及同 N 的低并行度、大工作集和部分中间 batch。它是有意选择的工程矩阵，不是所有 FFT 使用场景的随机样本。

26 个请求在所有 workload 上完整执行，筛选最多 936 次，具体请求以 JSON 为准：

- aimThreads 64/128/256 与 registerBoost 1/2/4。
- registerBoostNonPow2 0/1：源码在未启用时会把某些非 2 次幂 boost 退回。
- coalescedMemory 16/32/64/128：改变 strided 分解的可覆盖调度提示；真实设备线程、共享内存与 warp 上限不变。
- 普通 LUT 与 LUT_4step=-1 分别对照。LUT_4step=1 会强制普通 LUT 开启，二者不能视为完全独立。
- swapTo2Stage4Step=8192 和 swapTo3Stage4Step=65536，含 LUT 开/关和一个 coalescing 交互。
- 一个独立新进程 default_replica 作为负对照，排除在最优候选和模型目标之外。

registerBoost4Step 被库强制设回 1，因此不扫描。disableReorderFourStep 会省略最后转置、改变自然输出语义，因此不把它较少 kernel 的时间当本轮同任务加速。源码证据记录在 JSON。

26 个请求仍不是穷尽搜索。必须报告其实际产生的核心结构和源码/编译输入类别、参数折叠、编译/数值失败和资源预算排除。大量折叠本身是结果，不能用名义候选数量暗示广泛算法覆盖。

## 测量、正确性与污染门槛

主指标是 CUDA graph 内 R 次串行 forward 的事件区间除以 R。每次 forward 读取同一不可变输入；每个 graph sample 前在区间外恢复输入。它是固定工作集的重复执行稳态平均时间，不是普通 host API 一次调用的总延迟，也不意味着不同 batch 有相同缓存条件。

R 只用默认配置校准，目标原始 graph 区间至少 0.5 ms、上限 2048 次、最多 3 次调整；所有候选及复测冻结同一个 R。保留原始区间和未达目标标记。每进程热身 1 秒，筛选 31 samples，确认与 headline 101 samples。独立重复单位是进程中位数，不是一个进程里的 101 个 samples。

筛选按连续 workload block 运行，default 与 replica 位于两端，中间 24 个请求随机。N/batch block 顺序也固定随机；确认使用新的输入 seed 和进程，并交替基线的两端身份。所有候选检查一次 forward 和重复 graph 后的完整自然顺序输出、每个 batch 的误差和输入位级不变性：

```text
||GPU - reference||2 / (sqrt(N) * ||input||2) <= 1e-5
||GPU - reference||inf / ||input||2 <= 1e-4
```

要求全部输出有限，零输入精确输出零；保留逐点误差。新候选失败不能触发放宽阈值。CPU FP64 参考须保留直接 DFT 自测，GPU 的 zero/impulse/constant/quarter-tone 只能补充完整随机输入检查。

GPU guard 绑定真实 UUID，记录 pre/post 与每秒状态；发现本任务进程树以外的 compute PID 即停止并保存证据，不操作他人进程。总显存 2 GiB 是预先声明的资源预算，超出应标“预算不合格”，不能称数学错误。

同请求负对照源码/编译输入必须一致，时间比任一方向超过 5% 或样本前后四分位中位数漂移超过 5% 时隔离整个 block。不能只删除某个难看的候选行。恢复须经过安静窗口和固定健康对照；最多重复两个完整筛选 block，再失败就报告不完整，不无限修补。

## 筛选、确认与结论强度

筛选最小值称“测试集合筛选最优”，存在选择乐观偏差。随后冻结各 workload 的筛选 winner、一个核心结构不同的替代候选，以及全矩阵等权 log 比率选出的固定全局候选。全部 workload 做 3 轮新进程确认，包含 default 和 replica。

H1 主效应是冻结 winner 相对 default 的三轮配对 log 比率均值。不能在确认数据里重新挑最小值，再称为无偏确认最优。默认胜出时选择效果按定义为 1，不伪造统计检验。

最多 6 个 headline workload 按固定规则选择：最大确认收益、不同 N 的结构改变、同候选 crossover 的两个端点、最弱收益、默认最佳或最接近无变化的代表。空缺不以更多赢家补齐。选择和检验方向在新 10 轮配对数据之前冻结。

明确收益需点估计至少 5%、相对 2% 门槛的一侧配对 log 检验通过 Holm 校正，并满足 guard 和负对照。所有预先声明收益方向属于同一 family；负对照不算收益。零方差/量化限制不能产生假的无限 t 值或极小 p 值。真实 crossover 要求两边完全相同候选 ID，并且两个相反方向都独立通过；只换 aim 后对比笼统“boost策略”或 1% 排名变化都不够。

## 规划成本与实际 describe 原型

使用新 harness 和独立生成的 instrumentation 头覆盖，不改上游库。span 保留父子关系与 inclusive/exclusive 时间，覆盖配置查询、Scheduler、每 upload 资源/布局、host codegen、NVRTC、二进制提取、模块加载、属性、尾部临时分配和清理。不能把嵌套 inclusive 时间相加；要展示残差。API host 时间不一定等于异步设备工作完成时间，final sync 应单列。

describe 复用真实 Scheduler/layout/codegen，跳过 CompileKernel，在 app 尾部 temp allocation 前返回。它仍可能分配/上传 LUT，必须计时和释放，不能称纯 CPU、零资源或离线接口。整个调用链 compile/module-load/kernel-launch 都必须为零；在固定成本 workload/候选上逐 upload 比较 canonical 描述、源码和编译输入。重新 full 构建须使用不可变的原始请求，不能复用被 batch 折叠修改过的配置。逻辑寄存器与物理寄存器分开保存。

固定 8 个 workload 做 3 轮配对成本。每个 pipeline 为新进程和已初始化的 CUDA context，内部顺序构建/删除全部 26 个请求。两种 pipeline 是：

1. 全部请求 full 构建与清理。
2. 全部请求 describe 与清理，再 full 构建筛选已冻结的 winner。

两模式分别用 fresh context，内部 26 次共享 context；每轮交替模式顺序，并使用相同候选顺序。这样既避免把多个冷进程求和冒充真实搜索，也避免第一模式系统性预热第二模式。记录 context bootstrap、首次/后续操作和 pipeline wall，不能声称 OS/驱动/compiler 缓存完全冷。

第二模式的 winner 来自离线筛选，只能建立“已知选择时的描述枚举加一次构建”下界。模型推理、决策、fallback、实际 GPU 试跑搜索成本须另列。第一模式也只是全部候选构建成本，不是完整调优总时间。

describe 若未实现或一致性失败，明确报告 H3 可行性未建立/只在子范围成立；编译前日志不能替代成功的零编译路径。S0 可先做固定少量工程 smoke，不能作为 S3 的完整成本结论。

## 有限补充与停止规则

Nsight Compute 只预留 4 个固定 workload、每个 2 个候选：16384 的 B=1/2048 比较默认与 r4/NP1/LUT1；655360 的 B=1/51 比较默认与强制 3 stage。采集一次完整 forward 的 DRAM/L2、占用率和 launch 资源，记录 replay/cache 设置；profiler 时间不混主结果。当前 guard 尚未支持可靠 ncu 后代核验，状态为计划但未实施。若无法安全限定捕获/进程范围，记录未做并收紧机制主张，不阻塞主研究。

H4 仅在至少 12 个完整有效 N 分组时运行固定 ExtraTrees 消融，按 N 分组留出所有 batch/候选。主目标 log(candidate/default) 的默认时间仅用于训练标签；R、编译后寄存器、任何时间和有效性结果都不得进入编译前特征。只有 16 个 N 与一个设备，应明确域内、小样本限制。

完整动机需要分开的证据：重复收益说明存在优化空间；同候选双向 crossover 说明不能只换一套全局参数；实际低成本 describe 说明编译前选择具有实现基础。多个不同 N 上三者同时成立时证据较强。只有局部收益则只支持明确适用域的问题；默认普遍接近最优时应考虑局部启发式修补，而非预设普遍调优需求。

参数折叠、独立收益消失、没有明确 crossover、describe 成本高、模型没有优势，都是应保留的阴性结论。没有显著收益不等于已经证明 5% 内等价；三轮确认不足以给出窄上界的地方，保留不确定性。

完成固定筛选、3 轮确认、固定成本画像和最多 6 个 headline 的 10 轮后结束本轮。不因阴性结果自动增加 N、候选、模型或轮数。任何后续扩展都应基于本轮结果作为新的独立设计提出。
