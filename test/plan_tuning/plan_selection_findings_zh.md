# VkFFT 计划选择阶段总结

截至 2026-10-27。按用户要求停止修复和追加实验；本任务的 GPU 测试与遥测进程均已停止。本文使用已有结果，受共享 GPU 竞争影响的记录不进入有效性能结论。

当前证据支持研究“工作负载与实际计划结构之间的选择关系”，但尚不能证明学习模型已经优于 VkFFT 默认策略，也没有验证在线编译节省。比较有价值的现象是请求参数明显折叠，以及局部结构取舍随 batch 变化的线索。

## 已完成的测试

| 项目 | 范围或状态 |
|---|---|
| 库 | VkFFT 1.3.4，提交 `066a17c17068c0f11c9298d848c2976c71fad1c1`，原库未修改 |
| 设备 | 远端物理 GPU1，RTX 4090，CUDA 12.6 |
| 工作负载 | FP32、1D C2C forward；24 个仅含 2/3/5 因子的长度，各有单 batch 和约 256 MiB 输入的大 batch，共 48 个 |
| 候选 | 默认配置，加 `aimThreads={64,128,256}` × `registerBoost={1,2,4}` × `useLUT={-1,1}`，共 19 组 |
| 初筛 | 912/912 通过锁定的 criterion_v2 数值标准与输入不变性检查 |
| 数值交叉验证 | 独立 CPU 参考、直接 DFT/FFTW 对照通过；64 个解析 GPU 输入验证通过 |
| 性能口径 | 独立输入/输出，固定输入的 CUDA graph 重复执行；每工作负载冻结 R，1 秒预热，初筛 31 个样本；时间为一次完整 batch forward |
| 独立确认 | 已生成 91 条 round 0 记录，计划中的完整三轮未完成；未进行十轮追加检查 |

“数值通过”不等于“计时没有受干扰”。本次 criterion_v2 为按 batch 检查有限值及归一化 L2/最大误差的工程门槛；原逐点误差诊断也完整保留。测试未覆盖其他 GPU、后端、精度、多维 FFT、R2C、DCT 或素数长度。

## 观察一：名义参数空间远大于记录结构空间

| 每个 workload 的不同记录描述符数 | workload 数量 |
|---:|---:|
| 2 | 37 |
| 4 | 6 |
| 6 | 5 |

19 组请求平均对应 **2.67 类记录描述符**。如果仅比较上传次数、radix 和 block shape 等核心结构，则上述三组分别只有 1、2、3 类。

这说明请求参数与最终计划不是一一对应关系：启发式会归一化、覆盖或折叠不同请求。直接在原始 knobs 上搜索可能重复评估相近的计划，实际结构是值得研究的表示。

这里的相同仅指已记录字段相同，不证明生成源码、机器码或全部执行语义相同。因此不能据此宣称存在精确的 kernel 去重比例，也不能把 19→2.67 直接换算成编译节省。

## 观察二：完整未受影响子集里，默认参数通常已接近最佳观测值

独立遥测规则标记了 61 条初筛记录，涉及 37 个 workload；剩余 851 条未被标记。其中 **11 个 workload 的全部 19 个候选都未被标记**，可作完整的描述性候选比较。

| 这 11 个 workload 的默认时间／最佳观测时间 | 数值 |
|---|---:|
| 几何平均 | 1.0070× |
| 中位数 | 1.00094× |
| 最大值 | 1.03182× |
| 距最佳观测值不超过 2% | 10/11 |

最大值来自 `N=32768, batch=1024`：默认 1.161184 ms，`a64_r4_l1` 为 1.125376 ms。上述结果是存在选择偏差的初筛观测，尚无完成的多轮独立确认；这 11 个 workload 也不是全体 48 个的代表性抽样。它们支持“默认启发式在不少情形下已经较好”，不支持“普遍存在大幅调优空间”。

全部 11 项及计算来源见 [stage_summary_data.json](results/stage_summary_data.json)。

## 观察三：未受影响的局部记录仍提供结构选择线索

虽然 `N=16384, batch=2048` 的候选矩阵有一条被标记记录，以下两条初筛记录本身都在竞争窗口之外，启动显存也正常：

| 配置 | 上传次数 | 完整 batch 时间 |
|---|---:|---:|
| default | 2 | 1.163648 ms |
| `a128_r4_l1` | 1 | 0.579936 ms |

这一特定比较的时间比为 **2.0065×**。候选的 `localSize=[256,1,1]`、radix 序列为 `[32,32,8,2]`，与默认的两次上传结构不同。另一个请求配置 `a64_r4_l1` 形成了相同的已记录描述符；在竞争窗口结束后的**一轮**确认中，其时间为 0.580064 ms，默认为 1.164480 ms，等效默认对照为 1.164320 ms。

反过来，`N=16384, batch=1` 的两条未标记初筛记录中，默认等效配置 `a128_r1_l-1` 为 3.7975 μs，单上传候选 `a64_r4_l1` 为 8.8039 μs，前者约快 2.32×。这提示“更少上传次数”不能直接等同于“更快”；batch、并行度和资源占用需要共同考虑。该解释是待验证假设，尚未通过性能计数器确立因果机制。

这些记录可以作为探索性案例，**不能称为已充分复现的稳定加速或已完成的参数排名交叉实验**。两个 batch 的未标记初筛使用的请求配置不同，虽有记录结构一致性，仍不能偷换成同一参数的完整交叉验证。所有相关记录、时间和结构见 [stage_structural_case.json](results/stage_structural_case.json)。

## 学习模型目前能得出什么

已实现并运行预先固定的离线比较：工作负载＋请求参数、工作负载＋计划描述符、两者结合。主要目标是 `log(t_candidate/t_default)`，按 N 分组留出，避免同一 N 的 batch/候选跨训练集和测试集；编译后 CUDA 寄存器等属性不作为模型输入。

但该次完整模型评估使用了包含受影响标签的初筛数据，**其收益、regret 和排序指标不作为有效性能证据**。也不能因为绝对时间敏感性分析出现更好数字，就替换预定主要目标。现有结果没有建立“结构模型稳定优于参数模型或默认策略”的结论；这不等于证明结构信息没有价值。

原始离线输出作为诊断保留在 [screen_complete_snapshot/analysis](results/screen_complete_snapshot/analysis)，其中的最大加速比、总体平均和模型图不能作为最终收益图使用。

## initializeVkFFT 是否需要修改

当前实验**不需要修改**：枚举现有配置，完整初始化，读取实际结构，再测执行时间即可。这条路径已经实现。

未来要实现“所有候选先获得结构、模型评分、只编译选中候选”，则需要新增内部边界。`initializeVkFFT` 当前将调度、布局细化、LUT 准备、源码生成和编译交织在一起；部分特征到 host codegen 阶段才完整。`makeForwardPlanOnly` 只是只构建正向计划，不会跳过编译。

建议先做范围受限的 describe 接口：复用 Scheduler、layout 和 codegen，跳过编译与模块加载，导出有版本的值描述符；选中后从原始请求调用原初始化路径，并核验描述一致。LUT 等资源副作用及候选描述成本仍须计量。更彻底的纯规划接口应在之后拆分资源物化。

源码证据、位置和设计约束见 [planning_interface_design.md](planning_interface_design.md)。本轮未实现或测量该接口，因此没有在线编译避免或端到端成本收益。

## 可用于研究动机的表述

> VkFFT 的请求参数与实际执行计划并非一一对应，启发式会将多个参数组合映射为相同的已记录规划描述。初步观测还显示，结构取舍与 batch 等工作负载条件相关，少数配置存在明显的局部选择空间。因此，值得研究以工作负载和计划结构共同表示候选，并学习其相对执行代价。模型的排序优势及仅编译选中候选所带来的端到端收益，仍需后续独立验证。

不宜写成“默认启发式普遍较差”“结构模型已经证明更优”或“已实现先评分再编译”。

## 数据保留与当前停止点

竞争窗口按独立显存遥测确定，并对边界保守扩展；没有按执行快慢删点。完整窗口、阈值、61 个 key 及来源哈希保存在 [repair_decision_v1.json](results/anomaly_review/repair_decision_v1.json)。受影响的约 5.47× 最大筛选时间比不能作为调优收益。

用户要求先总结后，未开始修复或健康检查，也未完成追加测试。原始数据、数值诊断、污染快照和未完成的确认记录均保留。`gpu_guard.py` 与 `repair_design.json` 属于中断中的后续工作，不能视为已验收的可用恢复流程。
